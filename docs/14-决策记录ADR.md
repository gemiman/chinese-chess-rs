## ADR-001

### 自研中国象棋规则引擎，不引入第三方规则库

**状态**：已采纳 · 2026-09-23

**背景**

需要一套可靠的走法生成与规则裁决实现。Rust 生态中已有成熟的棋类库，先行调研是否有可复用方案。

**调研结果**（2026-09-23 实测 crates.io）

| Crate | 版本 | 是否可用 |
|---|---|---|
| `xiangqi_tui` | 0.1.0 | ❌ 是 TUI 客户端，非规则库；社区活跃度极低 |
| `xq` | 0.5.0 | ❌ 是 `jq` 的 Rust 重写，与象棋无关 |
| `shogi` | 0.12.2 | ❌ 将棋规则（持驹、升变、打入），与中国象棋完全不同 |
| `shakmaty` | 0.30.1 | ❌ 国际象棋及变体（王车易位、吃过路兵），无炮架/九宫/河界概念 |
| `chess` | 3.2.0 | ❌ 同上，面向国际象棋 |

**决策**

自研 `xq-core`。

**理由**

1. **无可选项**：上述库的规则体系（将棋/国际象棋）与中国象棋差异属于结构性差异，不存在"扩展适配"的可行路径——中国象棋特有的炮架、蹩马腿、塞象眼、九宫、河界、白脸将、长将长捉，在国际象棋/将棋库中没有任何对应抽象可复用。
2. **业务强依赖内部语义**：战法讲解需要知道每一步的**着法性质**（是将军、是捉子、是兑子、是弃子）。这些信息必须在走法生成的内部过程中提取。使用外部黑盒库则拿不到，需要二次解析，成本高于自研。
3. **权威裁决必须完全可控**：服务端裁决出错会导致用户判负争议，这属于产品信任底线。自研使每个判定都有对应的测试用例与可追溯的实现。
4. **性能自主可控**：走法生成是 AI 搜索的最内层热点。自研可使用位棋盘（bitboard）等优化，而不受外部库的抽象开销约束。

**权衡（代价）**

| 代价 | 缓解 |
|---|---|
| 开发工作量增加（预计 3~4 人周） | 规则本身是有限且确定的领域，无需求变更风险，投入一次到位 |
| 需要自行建立正确性信心 | 用**对拍题库**（≥3000 局面，来源：公开棋谱 + 手写边界用例）作为回归基线 |
| 需自行处理长捉等模糊规则 | 明确定义"可实现的简化判定表"并写入文档与 UI 提示，避免黑箱裁决 |

**后果**

- 新增 `xq-core` crate，成为整个项目的正确性基石。
- 必须有独立的规则测试套件，且其通过与否是 M0 里程碑的唯一准入条件。

## ADR-002

### 客户端采用 Tauri 2 + React，而非 egui / Slint

**状态**：已采纳 · 2026-09-23

**背景**

需求要求：Windows / Linux / macOS 三端原生客户端，且要做出接近 JJ 象棋的视觉表现（棋盘动画、讲解卡片、复杂布局）。同时前后端分离。

**候选方案对比**

| 维度 | **Tauri 2 + React** | egui | Slint | Bevy |
|---|---|---|---|---|
| UI 表现力（阴影/渐变/圆角/卡片） | ★★★★★（完整 CSS） | ★★（需手绘） | ★★★ | ★★★★ |
| 走子动画能力 | ★★★★★（CSS transition，GPU 合成） | ★★★（手写插值） | ★★★ | ★★★★★ |
| 中文排版（换行、字距、字体回退） | ★★★★★（浏览器级） | ★★ | ★★★ | ★★ |
| 文本输入（聊天、昵称） | ★★★★★ | ★★（IME 支持薄弱） | ★★★ | ★★ |
| 三端渲染一致性 | ★★★★（依赖系统 WebView） | ★★★★★（自带渲染） | ★★★★★ | ★★★★★ |
| 内存占用 | ★★★（WebView 约 80~150 MB） | ★★★★★（约 40 MB） | ★★★★★ | ★★★ |
| 安装包体积 | ★★★（约 8~15 MB） | ★★★★★（3~8 MB） | ★★★★★ | ★★ |
| 生态与组件库 | ★★★★★ | ★★ | ★★ | ★★ |
| **与团队既有技能栈匹配度** | ★★★★★（React + Vite + pnpm + TanStack Router） | ★★ | ★★ | ★★ |
| 无系统依赖 | ★★（Linux 需 webkit2gtk-4.1） | ★★★★★ | ★★★★★ | ★★★★★ |

**决策**

采用 **Tauri 2.11.6 + React + Vite + TypeScript**。

**理由**

1. **技能栈匹配是决定性因素**。团队已具备 React + Vite + pnpm workspace + TanStack Router 的完整经验，Tauri 的前端部分零学习成本；egui / Slint 则需要从零掌握新的 UI 范式与布局系统。
2. **产品形态需要浏览器级 UI 能力**。"战法讲解"面板是核心卖点，涉及长文本、富样式、可滚动历史、状态色标签、折叠展开——这些在 CSS 体系中是常规操作，在即时模式 GUI 中需要大量自绘工作。
3. **动画质量直接影响手感**。走子动画、棋子拖拽、合法落点脉冲提示，用 CSS `transform` + `transition` 天然走 GPU 合成层，实现 60 FPS 成本极低。
4. **Rust 侧职责不减**。规则、AI、讲解全部在 Rust 侧（Tauri command 暴露），前端只负责渲染——这正是我们想要的职责划分，不与"用 Rust 写核心"的目标冲突。

**权衡（代价与缓解）**

| 代价 | 缓解 |
|---|---|
| Linux 依赖 `webkit2gtk-4.1` 系统库 | 打包时用 AppImage / deb 声明依赖；文档明确列出各发行版安装命令 |
| 内存占用高于原生 GUI（WebView 开销） | 实测控制在内 NFR-P.10 的 300 MB 以内；避免前端加载大图与长列表虚拟化的缺失 |
| 不同平台 WebView 版本差异导致渲染不一致 | CI 加入三端视觉快照测试（`insta` + 截图对比） |
| Tauri 3.0 尚为 alpha | **锁定 2.11.6**，`tauri` 与 `tauri-build` 均不使用 3.x 预发布版 |

**后果**

- 项目包含 `frontend/`（React）与 `crates/xq-client`（Tauri Rust 侧）两部分。
- 前端性能成为一条独立的验收线（NFR-P.01 的 60 FPS 门禁）。

## ADR-003

### 客户端乐观更新 + 服务端最终权威裁决

**状态**：已采纳 · 2026-09-23

**背景**

联网对战中，走子反馈速度直接影响手感（NFR-P.02 要求 ≤ 16 ms）。若等服务器往返确认再渲染，体验会显著劣化（RTT 通常 30~150 ms）。

**候选方案**

| 方案 | 手感 | 一致性 | 复杂度 |
|---|---|---|---|
| A. 纯服务端权威（等确认再渲染） | 差（有 RTT 延迟） | 完美 | 低 |
| B. **乐观更新 + 服务端裁决**（选定） | 好（本地立即渲染） | 好（异常时回滚） | 中 |
| C. 客户端权威 | 最好 | **不可接受**（可被篡改） | 低 |

**决策**

方案 B。客户端本地用 `xq-core` 预校验并立即渲染，同时发送 `MoveRequest`；服务端用**同一份 `xq-core`** 重新裁决。裁决失败时下发 `MoveRejected` + 全量快照，客户端回滚并提示。

**理由**

1. 手感是交互产品的核心竞争力，50~150 ms 的延迟对棋类手感是可感知的劣化。
2. 由于两端共享同一个规则实现（ADR-005 的副产品），**合法着法在两端判定的结果必然一致** → 回滚是极小概率事件（仅在网络篡改或版本不一致时发生）。
3. 保留了服务端权威，不牺牲安全性（满足 NFR-S.01）。

**权衡**

| 风险 | 缓解 |
|---|---|
| 回滚造成视觉突兀 | 回滚时播放"棋子退回"动画 + 明确提示原因，而非瞬间跳变 |
| 客户端版本落后导致规则不一致 | 握手时进行**协议版本 + 规则版本**协商，不匹配则拒绝开局 |
| 恶意客户端伪造合法着法 | 服务端裁决兜底；非法一律拒绝并记录异常行为用于反作弊 |

**后果**

- `xq-protocol` 必须携带 `rules_version` 字段。
- 客户端必须有可靠的"回滚 + 重同步"状态机（这是前端状态管理的核心难点之一）。

## ADR-004

### 战法讲解采用"本地模板兜底 + LLM 增强"双层架构

**状态**：已采纳 · 2026-09-23

**背景**

"战法讲解"是产品核心差异点（FR-03）。需要决定讲解内容的生成方式。

**候选方案**

| 方案 | 离线可用 | 表达自然度 | 成本 | 延迟 | 可控性 |
|---|---|---|---|---|---|
| A. 纯本地模板 | ✅ | 中（模板化，略机械） | 零 | < 5 ms | 高（完全可控） |
| B. 纯 LLM | ❌ | 高 | 高 | 0.5~3 s | 低（可能幻觉） |
| C. **本地兜底 + LLM 增强**（选定） | ✅ | 高 | 可控 | 本地 5 ms / LLM 异步 | 高 |

**决策**

方案 C：
1. **本地路径**（`xq-coach`）：战术模式识别 + 引擎评分 → 填充结构化模板 → 输出讲解。**这条路径必须在任何情况下可用**，包括完全断网、无账号、LLM 服务故障。
2. **LLM 路径**：把本地生成的结构化分析（局面 FEN、着法、战术标签、引擎评分、候选着法列表）连同提示词交给 LLM，生成更自然的多句点评。
3. **降级策略**：LLM 调用失败 / 超时 / 返回内容不合法 / 触发日预算熔断 → **静默回退到本地模板结果**，用户无感知（FR-03.08）。

**理由**

1. **离线可用是硬需求**（NFR-R.06、FR-03.06）。纯 LLM 方案会让"没网就完全不能玩"，这不可接受。
2. **本地结果是 LLM 的"事实锚点"**。直接让 LLM 看棋盘容易产生幻觉（编造不存在的棋子位置与战法名称）。先由 `xq-core` / `xq-ai` 算出客观事实（这步走的是什么、评分损失多少、构成什么战术），再让 LLM 只做**语言润色**而非**事实推理**，可从根本上抑制幻觉。
3. **成本可控**。讲解按需生成、结果按局面哈希缓存（同一局面复用），并设置日预算熔断。

**权衡**

| 风险 | 缓解 |
|---|---|
| LLM 幻觉（编造战法名、错误评价） | LLM 只在给定的事实集合内措辞；输出经**事实校验**（如不得出现未在输入中出现的棋子坐标）；不通过则丢弃并回退本地 |
| LLM 延迟高（数秒） | 讲解是独立异步帧，**不阻塞走棋**；先推本地讲解，LLM 增强到达后**原地替换**该条卡片 |
| LLM 成本失控 | 日预算熔断 + 结果缓存 + 仅对"关键着法"（分档为疑/劣/漏，或用户主动请求）调用 LLM |
| LLM 服务不可用 | 100% 降级到本地模板，功能不缺失，仅表达丰富度下降 |

**后果**

- `xq-coach` 定义 `LlmClient` trait，保持本体零 IO（配合 ADR-005）。
- 需要 `assets/knowledge/` 下的模板库与战术模式库作为本地路径的知识基础。
- 讲解卡片在 UI 上支持"增强中 → 已增强"的渐进状态。

## ADR-005

### 领域层强制零 IO 依赖

**状态**：已采纳 · 2026-09-23

**背景**

规则、AI、讲解三个模块既要在服务端运行，又要在客户端运行。若它们直接依赖 `tokio` / `sqlx` / `reqwest`，将无法在客户端离线环境复用，且难以测试。

**决策**

`xq-core` / `xq-ai` / `xq-coach` **禁止**依赖：`tokio`、`axum`、`sqlx`、`sea-orm`、`redis`、`reqwest`、`hyper`、以及 `std::fs` / `std::net` / `std::time::SystemTime`。

CI 中以 `cargo tree` 做**依赖断言**（脚本检查禁用依赖是否出现在依赖树中），违反则构建失败。

**理由**

1. **可移植性**：同一份代码在服务端与客户端运行，消除规则分歧的根源（满足 NFR-M.01）。
2. **可测试性**：无时钟依赖 → AI 搜索可完全确定性复现；无网络 → 规则测试无需 mock。
3. **可 WASM 化**：零 IO 的 crate 编译 WASM 几乎无阻碍，为未来 Web 版留出路径。
4. **强制良好设计**：IO 被推到应用层，领域层只剩纯函数，天然 `Send + Sync`，可自由并行化。

**例外与处理**

| 需求 | 处理方式 |
|---|---|
| 讲解需要调用 LLM | 定义 `LlmClient` **trait**，实现放在应用层注入 |
| 引擎需要随机数（难度抖动） | 使用 `rand` 的**显式种子** `StdRng`，由调用方传入，而非 `thread_rng()` |
| 引擎需要限时搜索 | 使用**逻辑节点计数上限**而非墙钟时间；由应用层通过 `AtomicBool` 从外部打断 |

**后果**

- 应用层承担所有 IO 编排职责，`xq-server` / `xq-client` 的代码量会相应增加。
- 需要额外维护 CI 依赖断言脚本（见 [docs/11](11-工程规范与CI-CD.md)）。

## ADR-006

### 服务端房间采用 Actor 模式而非共享锁

**状态**：已采纳 · 2026-09-23

**背景**

每个对局房间需要维护状态（棋盘、双方身份、计时、观战者列表、待决请求），并被多方并发访问（双方玩家的帧、观战者的订阅、计时器触发）。

**候选方案**

| 方案 | 一致性保证 | 死锁风险 | 计时器实现 | 崩溃隔离 |
|---|---|---|---|---|
| A. `DashMap<RoomId, Arc<Mutex<Room>>>` | 需谨慎设计锁顺序 | 有 | 需全局扫描任务 | 差（锁中毒） |
| B. **每房间一个 Tokio task + mpsc**（选定） | 天然串行化 | 无 | 房间内 `interval` | 好（task 隔离） |

**决策**

方案 B。每个房间是一个独占的 Actor task，通过 `mpsc::Receiver<RoomCommand>` 接收所有变更指令，通过 `oneshot` 返回需要应答的结果。

**理由**

1. **状态机天然串行**：房间状态变更（走子、认输、超时、加入观战）本质是串行的。Actor 模型把并发问题转化为消息队列问题，从根上消除锁竞争与死锁。
2. **计时器内聚**：每个房间自带 `tokio::time::interval` 驱动 `Tick`，无需全局定时任务扫描所有房间（方案 A 需要扫全表，房间数上升后成为瓶颈）。
3. **崩溃隔离**：单房间 panic 只销毁该 task，其他房间不受影响。共享锁方案一旦中毒会波及所有持有者。
4. **容量无虞**：2500 房间 × 约 8 KB task 开销 ≈ 20 MB；Tokio 支撑十万级 task 无压力。

**权衡**

| 代价 | 缓解 |
|---|---|
| 每房间一个 task 的内存开销 | 已在容量核算中确认可忽略（20 MB） |
| 跨房间操作（如全局大厅列表）需额外机制 | 大厅列表维护在 Redis + 独立的轻量索引，不由房间内查 |
| 消息队列成为潜在瓶颈 | 单房间消息速率极低（人类每几秒一步），无压力 |

**后果**

- `room/` 模块需要一个清晰的 `RoomCommand` 枚举作为房间的唯一入口。
- 房间状态的持久化快照需通过 `Snapshot` 命令导出（不直接读内部字段）。

## ADR-007

### 通信协议采用 JSON，预留二进制扩展

**状态**：已采纳 · 2026-09-23

**背景**

需要为 REST 与 WebSocket 选择序列化格式。

**数据量实算**

- 单个 `MoveApplied` 帧 JSON ≈ 180~260 字节
- 单局约 80 回合 = 160 步 → 走棋帧 ≈ 42 KB
- 讲解帧约 400 字节 × 160 ≈ 64 KB
- **合计 ≈ 106 KB / 局**

**服务端负载推算**（2500 并发对局，平均 10 秒一步）

- 帧速率 ≈ 2500 ÷ 10 = **250 帧/秒**
- 出站带宽 ≈ 250 × 300 B ≈ **75 KB/s**（未含观战广播，量级仍在 1 MB/s 以内）

**决策**

采用 JSON（`serde_json`），并在协议头保留 `v`（版本）与可选编码模式字段，为未来切换到 MessagePack / Protobuf 留出空间。

**理由**

1. **带宽与 CPU 开销在此量级完全不是瓶颈**（75 KB/s 对现代服务端微不足道）。为不存在的性能问题引入二进制格式的复杂度，是过早优化。
2. **可调试性价值极高**：抓包即可读懂帧内容，问题定位成本大幅降低。对开发与线上排障都是实质收益。
3. **前后端天然共享**：Tauri 前端（JS）可直接消费 JSON，无需额外解码层。
4. **演进成本低**：如果未来观战规模或帧频率大幅上升，可基于已有的版本字段平滑引入二进制模式，而不破坏现有客户端。

**权衡**

| 代价 | 缓解 |
|---|---|
| 体积大于二进制格式约 2~3 倍 | 实算确认不影响；必要时开启 WS 的 `permessage-deflate` |
| 解析开销高于二进制 | `serde_json` 解析微秒级，相对于帧速率可忽略 |
| 数字精度（如大整数 ID） | 统一用字符串传递 UUID，避免 JS Number 精度问题 |

**后果**

- `xq-protocol` 的所有帧须带 `type` 判别标签。
- 客户端必须优雅忽略**未知帧类型**，以便服务端先行上线新功能。

## ADR-008

### 棋盘渲染采用 SVG + DOM + CSS Transform，而非 Canvas

**状态**：已采纳 · 2026-09-23

**背景**

棋盘渲染方案直接影响动画流畅度、开发效率与可访问性。

**对比**（棋子数恒为 32，棋盘线为静态）

| 维度 | Canvas 2D | SVG + DOM（选定） |
|---|---|---|
| 动画实现 | 需手写 `requestAnimationFrame` 插值 + 全量重绘 | CSS `transition` / `transform`，浏览器 GPU 合成 |
| 命中测试 | 需自行实现坐标 → 棋子的反查 | 浏览器原生（`event.target`） |
| 高 DPI | 需手动处理 `devicePixelRatio` 缩放 | 矢量自动清晰 |
| 可访问性 | 需额外 ARIA 层 | 每个棋子是真实 DOM 节点，天然可标注 |
| 调试 | 只能看像素，无法 inspect | DevTools 直接选中元素、看样式、看布局 |
| 元素数量 | 1 个 canvas | 约 32 棋子 + 棋盘背景（几十个节点） |
| 重绘成本 | 每帧全画 | 只重绘变化的节点（浏览器自动 diff） |
| 上限 | 极高（千级精灵） | 中高（数百节点） |

**决策**

- 棋盘线框：**静态 SVG**（`assets/board/board-classic.svg`），作为背景图片一次性加载。
- 棋子：**绝对定位的 DOM 节点**，位置通过 `transform: translate(x, y)` 控制。
- 动画：CSS `transition`（移动、淡入、高亮脉冲）。
- 高亮层：独立 SVG overlay，绘制合法落点标记与推荐着法箭头。

**理由**

1. **32 个节点远低于 DOM 性能上限**。浏览器对数十个元素的合成层优化非常成熟，60 FPS 无压力（满足 NFR-P.01）。Canvas 的"高性能"优势在这个量级上完全体现不出来。
2. **`transform` 走 GPU 合成**，动画期间不触发布局与重绘，比 Canvas 全量重绘更省。
3. **可访问性是硬需求**（NFR-U.04 键盘操作）。DOM 节点天然可获得焦点、可被屏幕阅读器识别；Canvas 需要从零构建 ARIA 镜像层，成本高且易错。
4. **开发与调试效率**。可直接在 DevTools 中选中某枚棋子查看其坐标与样式，这对调试"棋子错位""缩放错位"这类高频 UI 问题价值巨大。
5. **素材已就绪**，SVG 棋盘与棋子素材已生成（`assets/board/`、`assets/pieces/`），矢量在任何缩放下都清晰。

**权衡**

| 代价 | 缓解 |
|---|---|
| 理论上元素数上限低于 Canvas | 本场景固定 32 枚棋子，无风险 |
| 拖拽时需自行处理坐标换算 | 一次实现（棋盘坐标 ↔ 像素坐标）并配单元测试 |
| SVG 背景若内联会增大 DOM 体积 | 使用 `<img src>` 引用外部 SVG 文件，保持 DOM 简洁 |

**后果**

- 前端需要一个纯粹的坐标换算模块（ICCS ↔ 像素），并有对应测试。
- 棋盘缩放通过容器尺寸 + CSS 变量驱动，所有棋子位置由 CSS 变量计算，天然支持响应式。

## ADR-009

### 主存储采用 PostgreSQL + SeaORM

**状态**：已采纳 · 2026-09-23

**决策**

PostgreSQL 16+ 作为主数据库，SeaORM 2.0.3 作为 ORM 与迁移工具。

**理由**

1. **数据形态高度关系化**：用户、对局记录、着法明细、积分变动、举报工单——典型的关系模型，且对局与着法是明确的 1:N 关系。
2. **需要事务**：对局结束时的"写战绩 + 更新积分 + 写积分流水"必须原子，PostgreSQL 的事务能力是刚需。
3. **JSONB 支持**：棋谱着法序列、讲解历史等半结构化数据可用 JSONB 存储，兼顾灵活性与可查询性。
4. **SeaORM 与团队经验匹配**，且其迁移体系（`sea-orm-migration`）支持版本化演进。
5. **已在工作区其他项目中使用**，运维与调优经验可复用。

**权衡**

| 代价 | 缓解 |
|---|---|
| 相比 SQLite 需要独立部署 | 开发环境用 Docker Compose 一键启动 |
| 相比嵌入式 DB 增加了运维面 | 单实例规模下运维成本可接受 |

**后果**

- 所有 schema 变更必须通过迁移文件，禁止手改生产库。
- 见 [docs/09-数据模型与存储设计.md](09-数据模型与存储设计.md)。

## ADR-010

### Redis 的职责边界严格限定

**状态**：已采纳 · 2026-09-23

**决策**

Redis 只承担以下四类职责，**不作为主存储**：

| 用途 | 数据结构 | 说明 |
|---|---|---|
| 对局房间状态快照 | String / Hash，带 TTL | 支撑服务重启后的房间恢复 |
| 匹配队列 | Sorted Set（score = 等级分） | 按分段检索候选对手 |
| 着法持久化缓冲 | **Stream** | 异步落库的中间层（见 ADR-011） |
| 会话与限流 | String + 计数器（带 TTL） | refresh token 白名单、接口限流 |

**明确不用于**：
- 用户资料、战绩等**权威数据**（必须落 PostgreSQL，Redis 丢失不可影响业务正确性）；
- 棋谱终态（必须落 PostgreSQL，Redis 只能作为过程缓冲）。

**理由**

1. **Redis 的持久化保证弱于 PostgreSQL**（AOF 也可能丢最后若干秒）。用于权威数据会引入数据丢失风险。
2. **职责清晰可降低认知负担**：一切"丢了可以重建"的数据放 Redis；"丢了就出事"的数据放 PostgreSQL。
3. **Stream 天然适合做异步落库缓冲**：支持消费者组、ACK 机制、重放，比 List 更合适。

**后果**

- 所有 Redis 写入必须有 TTL（除 Stream 由 `MAXLEN` 限制），避免内存无界增长。
- 关键键名规范见 [docs/09](09-数据模型与存储设计.md)。

## ADR-011

### 着法持久化异步化（Redis Stream → PostgreSQL）

**状态**：已采纳 · 2026-09-23

**背景**

每步棋都需要落库（NFR-R.04 要求最多丢 1 步）。若在走棋关键路径上同步写 PostgreSQL，会把 DB 延迟直接引入对局延迟（违反 NFR-P.07 的 P99 ≤ 100 ms）。

**决策**

走棋路径上只做 **`XADD` 到 Redis Stream**（微秒级），由独立的消费者任务批量（batch）写入 PostgreSQL。

```
走棋裁决通过
    → XADD game:{game_id}:moves {seq, mv, clock, ts}
    → 立即广播 MoveApplied（不等落库）
    
消费者（独立 task）
    → XREADGROUP 批量取（如每次最多 100 条 / 最多等 100 ms）
    → 批量 INSERT 到 PostgreSQL（单事务）
    → XACK
```

**理由**

1. **走棋路径零 DB 依赖**：对局延迟只受 Redis 与网络影响（Redis 单次 `XADD` 通常 < 1 ms，实际多为 0.1 ms 级）。
2. **批量写入提升 DB 吞吐**：逐条 INSERT 的 250 次/秒 与批量 INSERT 的开销差异显著，且批量事务减少了 fsync 次数。
3. **崩溃可恢复**：消费者在 ACK 前崩溃，消息仍在 Stream 的 Pending 列表中，重启后可重新消费。
4. **削峰**：DB 短暂不可用时，Stream 可缓冲，不阻塞对局。

**权衡**

| 风险 | 缓解 |
|---|---|
| 落库存在延迟，极端情况可能丢数据 | 延迟为百毫秒级；ACK 前崩溃可重放；NFR-R.04 允许丢 1 步 |
| Stream 内存增长 | 使用 `MAXLEN ~ 10000` 近似裁剪；消费者组保证未 ACK 的保留 |
| 消费端成为单点 | 消费者为独立 task，崩溃由 supervisor 重启；PG 侧用 upsert 保证幂等 |

**后果**

- 需要对 `(game_id, seq)` 建唯一索引，配合 `ON CONFLICT DO NOTHING` 实现幂等落库。
- 消费者需要处理"对局已结束但 Stream 仍有残留"的边界情况。

## ADR-012

### 观战统一施加 3 秒延迟

**状态**：已采纳 · 2026-09-23

**背景**

若观战流实时转发，观战者可通过外部通讯把实时局面传给对局中的一方，构成作弊通道。

**决策**

服务端为每个观战连接维护一个**延迟队列**：帧进入队列后，延迟 3000 ms 再下发。对局双方不经过该队列（实时）。

**理由**

1. **3 秒足以破坏即时作弊的价值**：象棋中一步的决策时间通常为秒到分钟级，3 秒延迟意味着传递信息的收益低于直接思考的成本，且传递本身也需要时间。
2. **服务端实现，不依赖客户端**：客户端无法绕过（满足 NFR-S.03）。
3. **对观战体验影响可接受**：观战者看的是策略与思路，3 秒延迟几乎不可感知。

**权衡**

| 代价 | 缓解 |
|---|---|
| 观战者看到的是过去 3 秒的局面 | 产品上可接受；UI 明确标注"观战延迟 3 秒"以避免困惑 |
| 服务端需为每个观战者维护队列内存 | 每观战者队列最多缓存 3 秒的帧（约 1 帧/10 秒 → 至多 1 条），内存可忽略 |

**实现要点**

延迟队列不用"每条消息各起一个 `sleep` task"（2500 房间 × 50 观战者会产生大量 task），而采用**统一的分片定时推送**：按 1 秒分片，推送 3 秒前那个分片累积的帧。

**后果**

- 观战语义上不等于"实时"，需求与文档需一致表述（FR-06.04）。

## ADR-013

### 内部坐标统一用 ICCS，中文记谱仅作展示层

**状态**：已采纳 · 2026-09-23

**决策**

- **内部表示**：ICCS 坐标，列 `a`..`i`（对应索引 0..8），行 `0`..`9`（`0` = 红方底线，`9` = 黑方底线）。
- **持久化与交换**：FEN。
- **中文记谱**（如"炮二平五"）：仅作为**展示层与棋谱文本**，由 `xq-core::notation` 在内部表示与中文记谱之间双向转换。

**理由**

1. **ICCS 无歧义且可索引**：`(col, row)` 是二维索引，算法层可直接寻址，无需解析字符串。
2. **中文记谱有内在歧义需要消解**：同一直线存在两个同类棋子时，必须用"前/后"区分（如"前马进七"）；且红黑双方的"路数"计算方向相反（红方从右往左数 1..9，黑方从黑方视角从右往左数 1..9，即列索引加 1）。这些复杂性只应存在于展示层。
3. **交换格式需要标准**：FEN 是棋类通用的局面描述格式，便于导入导出与第三方工具互通。

**关键对照（实现基准）**

| 项 | 规则 |
|---|---|
| 列 | `a`=0 … `i`=8（从红方视角，**红方最左侧为 a**） |
| 行 | `0` = 红方底线，`9` = 黑方底线 |
| 红方路数 | `9 - col`（列 i=8 → 一路；列 a=0 → 九路） |
| 黑方路数 | `col + 1`（列 a=0 → 1 路；列 i=8 → 9 路） |
| 验证 | 红 "炮二平五"：红二路 = col 7 = h 列，炮 h2 → e2 ✔<br/>黑 "炮8平5"：黑 8 路 = col 7 = h 列，炮 h7 → e7 ✔ |

**后果**

- 记谱模块需要覆盖"前/后"消歧、进/退/平的语义解析，并有完备测试。
- 详见 [docs/03-规则引擎与领域模型.md](03-规则引擎与领域模型.md)。

## ADR-014

### 对局时钟以服务端为唯一权威

**状态**：已采纳 · 2026-09-23

**决策**

- 服务端维护每方的剩余时间（毫秒），每次走子时扣除；
- 客户端**不参与**时间的权威计算，仅做本地插值显示；
- 服务端定期下发 `ClockSync` 帧（含服务端时间戳与双方剩余时间）校正客户端显示；
- 超时判定完全由服务端作出。

**理由**

1. **客户端时间可被篡改**（改系统时间、改本地存储、劫持 IPC）。若时间参与判定，作弊成本极低。
2. **网络抖动不应惩罚玩家**：服务端以"收到合法走子帧的服务端时间"为准扣除，并预留网络宽限（grace period），避免因丢包导致误判超时。
3. **本地插值保证显示平滑**：无需每秒请求服务端，客户端自行递减显示，每 5~10 秒由 `ClockSync` 校正一次即可。

**权衡**

| 风险 | 缓解 |
|---|---|
| 客户端显示与服务端存在偏差（最多一个同步周期） | 同步周期 5 秒，偏差 ≤ 数十字节级；对局中显示合理 |
| 网络延迟导致"看起来没超时却判超时" | 引入宽限窗口（如 500 ms）+ 客户端明确提示 |
| 玩家网络差被误判 | 断线单独走重连逻辑（120 秒席位保留），不直接判超时 |

**后果**

- `ClockSync` 帧必须在协议中定义（见 [docs/06](06-联网对战与实时通信协议.md)）。
- 超时判定逻辑需要专门的测试用例覆盖网络抖动场景。

## 1. 设计目标

| 目标 | 指标 |
|---|---|
| 正确性 | 对拍题库 ≥ 3000 局面 100% 通过；perft 各深度与公认值一致 |
| 性能 | 走法生成 ≥ 10M positions/s（`cargo bench` 实测）；perft(4) 在 1 秒内完成 |
| 内存 | 单个 `Position` 结构 < 1 KB（含历史），支撑 AI 搜索中数百万次 make/unmake |
| 无 IO | 不依赖任何 IO crate，不使用 `SystemTime`（见 ADR-005） |
| 可复现 | 相同输入必然产生相同输出，无隐藏随机源 |

## 2. 坐标系统

### 2.1 三个坐标系及其职能

| 坐标系 | 用途 | 说明 |
|---|---|---|
| **ICCS 坐标** | **内部唯一表示** | 列 `a`..`i` = 索引 0..8；行 `0`..`9`，`0` = 红方底线 |
| **FEN** | 持久化与交换 | 标准棋类局面描述 |
| **中文记谱** | 展示与棋谱文本 | 如"炮二平五"，仅由 `notation` 模块在边界处转换 |

### 2.2 棋盘方位约定

```
        a    b    c    d    e    f    g    h    i      ← ICCS 列 (col 0..8)
      ┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
 row 9│ 車 │ 馬 │ 象 │ 士 │ 將 │ 士 │ 象 │ 馬 │ 車 │  黑方底线
 row 8│    │    │    │    │    │    │    │    │    │
 row 7│    │ 砲 │    │    │    │    │    │ 砲 │    │  黑炮
 row 6│ 卒 │    │ 卒 │    │ 卒 │    │ 卒 │    │ 卒 │  黑卒
 row 5│    │    │    │    │    │    │    │    │    │  ← 黑方半场
      ├────┴────┴────┴────┴────┴────┴────┴────┴────┤
      │              楚  河        汉  界            │  ← 河界（row 4 与 row 5 之间）
      ├────┬────┬────┬────┬────┬────┬────┬────┬────┤
 row 4│    │    │    │    │    │    │    │    │    │  ← 红方半场
 row 3│ 兵 │    │ 兵 │    │ 兵 │    │ 兵 │    │ 兵 │  红兵
 row 2│    │ 炮 │    │    │    │    │    │ 炮 │    │  红炮
 row 1│    │    │    │    │    │    │    │    │    │
 row 0│ 车 │ 马 │ 相 │ 仕 │ 帅 │ 仕 │ 相 │ 马 │ 车 │  红方底线
      └────┴────┴────┴────┴────┴────┴────┴────┴────┘
```

**关键方位定义**（后续所有规则描述均以此为准）：

| 概念 | 定义 |
|---|---|
| 红方半场 | `row ∈ [0, 4]` |
| 黑方半场 | `row ∈ [5, 9]` |
| 河界 | `row 4` 与 `row 5` 之间 |
| 红方前进方向 | `row` 递增 |
| 黑方前进方向 | `row` 递减 |
| 红方九宫 | `col ∈ [3, 5]` 且 `row ∈ [0, 2]` |
| 黑方九宫 | `col ∈ [3, 5]` 且 `row ∈ [7, 9]` |

### 2.3 路数换算（中文记谱的根基）

红黑双方各自从**自己的右侧**数 1..9 路：

| 方 | 路数公式 | 验证 |
|---|---|---|
| 红方 | `route = 9 - col` | 列 `i`(8) → 1 路（红方最右）；列 `a`(0) → 9 路（红方最左） |
| 黑方 | `route = col + 1` | 列 `a`(0) → 1 路（黑方视角最右）；列 `i`(8) → 9 路 |

> **为什么黑方是 `col + 1`**：黑方在上方，面向南方，其右手边是棋盘的西侧（`a` 列）。故黑方 1 路 = `a` 列。

**双向验证**（这两个例子必须能通过测试）：

- 红方「**炮二平五**」：红二路 → `col = 9 - 2 = 7` = `h` 列；红炮初始在 `h2`，平至五路（`col = 9 - 5 = 4` = `e` 列）→ 着法 `h2 → e2`。这是经典"当头炮"，正确。
- 黑方「**炮8平5**」：黑 8 路 → `col = 8 - 1 = 7` = `h` 列；黑炮初始在 `h7`，平至 5 路（`col = 5 - 1 = 4` = `e` 列）→ 着法 `h7 → e7`。黑方应对中炮的标准着法，正确。

## 3. 棋盘表示

### 3.1 选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 二维 `[[T; 9]; 10]` | 直观 | 行优先索引需两次乘法；缓存局部性一般 | 否 |
| **一维 `[u8; 90]`** | 单次偏移、缓存友好、易序列化 | 需人工保证 `row*9+col` 正确性 | **采纳** |
| 纯位棋盘 | 最快 | 炮的"隔一子"语义不适配；开发复杂度高；调试困难 | 否 |
| 混合：数组 + 占据位图 | 兼顾简洁与速度 | 需维护两者一致性 | **采纳** |

**最终方案**：一维数组作为**唯一真相源**，辅以两个 `u128` 占据位图加速攻击检测。位图是**派生数据**，只在 `make_move` / `unmake_move` 中增量维护。

```rust
/// 90 格一维数组，索引 = row * 9 + col
pub const BOARD_SIZE: usize = 90;

/// 格子编码：0 = 空；红方 1..=7；黑方 9..=15
/// 编码公式：empty=0, piece = kind | (color << 3)
pub type Square = u8;

pub const EMPTY: Square = 0;

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
#[repr(u8)]
pub enum PieceKind {
    King     = 1,  // 帅 / 将
    Advisor  = 2,  // 仕 / 士
    Elephant = 3,  // 相 / 象
    Horse    = 4,  // 马
    Chariot  = 5,  // 车
    Cannon   = 6,  // 炮
    Pawn     = 7,  // 兵 / 卒
}
```

> 编码中 `kind` 占低 3 位（1..7），`color` 占第 4 位。红方 `color = 0`（编码 1..7），黑方 `color = 1`（编码 9..15）。这样"是否为空"只需判断 `== 0`，比 `Option<T>` 省一次分支，且天然适合数组索引。

### 3.2 核心结构

```rust
#[derive(Clone)]
pub struct Position {
    /// 90 格棋盘，唯一真相源
    squares: [Square; BOARD_SIZE],
    /// 红方占据位图（派生）
    red_occ: u128,
    /// 黑方占据位图（派生）
    black_occ: u128,
    /// 当前走子方
    side_to_move: Color,
    /// 红方将帅所在格（缓存，避免每次扫描）
    red_king_sq: u8,
    /// 黑方将帅所在格（缓存）
    black_king_sq: u8,
    /// 距上次吃子的半步数（用于 60 回合自然限着）
    halfmove_clock: u16,
    /// 回合数
    fullmove_number: u16,
    /// Zobrist 哈希（增量维护）
    hash: u64,
    /// 历史局面哈希栈（用于重复局面检测与悔棋）
    history: Vec<u64>,
    /// 历史着法栈（用于 unmake_move 与终局判定）
    move_stack: Vec<MoveRecord>,
}
```

**内存核算**：`squares` 90 B + 两个 u128 共 32 B + 标量约 20 B + `history` 约 80 步 × 8 B = 640 B + `move_stack` 约 80 × 16 B = 1280 B。

> ⚠️ `move_stack` 是最大项。AI 搜索中每层需要独立的 `Position` 克隆会带来显著开销。**优化方案**：搜索时使用单个 `Position` 配合 `make_move` / `unmake_move` 的就地修改，**不克隆整个结构**；`move_stack` 与 `history` 容量预分配（`with_capacity(256)`）避免反复扩容。裸 `Position`（不含栈）约 **140 B**，远低于 1 KB 目标。

## 4. 走法生成

### 4.1 两阶段架构

```
第一阶段：生成伪合法着法（pseudo-legal）
    —— 只考虑棋子自身的走法规则（含蹩马腿、塞象眼、炮架等）
    —— 不检查"走完后己方将帅是否被将军"

第二阶段：过滤（合法化）
    —— 对每个伪合法着法执行 make_move
    —— 用 is_attacked(己方将帅, 对方) 检测是否被将军
    —— 被将军则 unmake_move 并剔除该着法
```

**为什么用"make/unmake + 攻击检测"而不是"预生成对方攻击位图"**：中国象棋中"炮"和"马"的攻击关系无法用静态位图穷举（炮依赖炮架、马依赖蹩腿点，都与实时局面相关），预生成位图需要额外维护且易错。make/unmake 方案实现简单、正确性易验证，且在实际引擎中被广泛采用。

### 4.2 各棋子走法规则（精确描述）

#### 车（Chariot）

四方向射线延伸。沿途空格可走；遇到**第一个**棋子时：若为敌方则可吃并终止，若为己方则不可走并终止。

#### 马（Horse）

八个目标，各有一个**蹩马腿**点。马在 `(c, r)`：

| 目标偏移 | 蹩腿点（相对 `(c,r)`） |
|---|---|
| `(c-1, r+2)`、`(c+1, r+2)` | `(0, +1)` |
| `(c-1, r-2)`、`(c+1, r-2)` | `(0, -1)` |
| `(c+2, r-1)`、`(c+2, r+1)` | `(+1, 0)` |
| `(c-2, r-1)`、`(c-2, r+1)` | `(-1, 0)` |

**规则**：目标点须在棋盘内且非己方子；**蹩腿点必须是空格**，否则该方向的两个目标均不可走。

> 注意：蹩腿点只需是**空**，与目标点是什么棋子无关。

#### 相 / 象（Elephant）

四个斜向目标 `(±2, ±2)`。**田字中心点** `(c±1, r±1)` 必须是空格（塞象眼）。**不可过河**：

- 红方相：目标 `row ∈ [0, 4]`
- 黑方象：目标 `row ∈ [5, 9]`

因此红相只能到达 7 个固定点：`(2,0) (6,0) (0,2) (4,2) (8,2) (2,4) (6,4)`；
黑象：`(2,9) (6,9) (0,7) (4,7) (8,7) (2,5) (6,5)`。

#### 仕 / 士（Advisor）

四个斜向一步 `(±1, ±1)`，且目标必须在**己方九宫**内。

#### 帅 / 将（King）

四个直向一步 `(±1, 0)`、`(0, ±1)`，且目标必须在**己方九宫**内。

**额外规则（白脸将）**：将帅不可在同一直线上无子相隔（见 4.4 节）。

#### 炮（Cannon）

四方向射线，但**走子与吃子规则不同**：

| 行为 | 规则 |
|---|---|
| **移动（目标为空）** | 照车的方式：遇到第一个棋子前的所有空格均可走 |
| **吃子（目标为敌子）** | 起点与目标之间必须**恰好有一个棋子**（炮架），且该炮架可以是任意方棋子 |

#### 兵 / 卒（Pawn）

| 方 | 未过河 | 过河后 |
|---|---|---|
| 红兵 | `row ∈ [0,4]`：仅可 `(0, +1)` | `row ∈ [5,9]`：可 `(0, +1)` 与 `(±1, 0)` |
| 黑卒 | `row ∈ [5,9]`：仅可 `(0, -1)` | `row ∈ [0,4]`：可 `(0, -1)` 与 `(±1, 0)` |

**兵卒永不后退**，且横向移动只能一步。兵卒走到对方底线后横向移动能力保留（俗称"老兵"，价值大幅下降但不失去走法）。

### 4.3 特殊情况：将帅照面

将帅位于同一列且中间无任何棋子时，该局面为**非法**（俗称"白脸将"）。这意味着：

1. **不能走出**导致将帅照面的着法；
2. 在伪合法着法生成时，允许生成"帅沿同列直线吃到对方将"的虚拟着法用于**攻击检测**——这样把照面规则统一为攻击关系，避免单独写一套判定。

**统一的攻击检测模型**：把将帅视为"沿同列直线、中间无异子时可攻击对方将帅"，即可让 `is_attacked` 同时覆盖常规将军与白脸将两种情况。

### 4.4 攻击检测 `is_attacked(sq, by_color)`

**方向**：给定格子 `sq` 与攻击方颜色，判断该格是否被攻击。采用**反向探测**（从目标点反查攻击者），比正向生成全部着法快得多。

| 攻击者 | 探测方式 |
|---|---|
| 车 / 将帅（同列） | 沿 4 个方向延伸，遇**第一个**棋子：若为敌方车 → 被攻击；若为敌方将帅且方向为纵向 → 被攻击（白脸将） |
| 炮 | 沿 4 个方向延伸，跳过第一个棋子（炮架）后，遇**第二个**棋子：若为敌方炮 → 被攻击 |
| 马 | 检查 8 个"马可能来自"的位置，反推其蹩腿点是否为空 |
| 兵 / 卒 | 检查红兵可能来自 `sq + (0,-1)`（红兵向下攻击视为…见下） |

**兵卒的反向探测（易错点）**：

- 红兵**向前**（`row+1`）吃子。故若 `sq` 被红兵攻击，则该红兵位于 `sq` 的 `(0, -1)`（即 `row` 小一格）——且需 `sq.row >= 5`（红兵已过河才能横吃，此处是纵向攻击故始终成立）。
- 红兵**横向**吃子。若 `sq.row >= 5`（已过河），则红兵也可能位于 `sq ± (1, 0)`。
- 黑卒反之：位于 `sq + (0, +1)`，以及 `sq.row <= 4` 时的 `sq ± (1, 0)`。

**将帅相邻攻击**：将帅在九宫内可直走一步攻击，故也需检查 4 邻位是否有敌方将帅。

## 5. 终局判定

### 5.1 判定流程

```rust
pub fn status(&mut self) -> GameStatus {
    let in_check = self.is_in_check(self.side_to_move);
    let has_legal_move = self.any_legal_move();   // 短路：找到第一个即返回

    if !has_legal_move {
        // 中国象棋：无着可走即负，无论是否被将军
        return if in_check {
            GameStatus::Checkmate { loser: self.side_to_move }   // 将死
        } else {
            GameStatus::Stalemate { loser: self.side_to_move }   // 困毙
        };
    }

    if self.halfmove_clock >= 120 {            // 60 回合 = 120 个半步
        return GameStatus::Draw { reason: DrawReason::SixtyMoveRule };
    }

    if self.is_insufficient_material() {       // 双方均无进攻子力
        return GameStatus::Draw { reason: DrawReason::InsufficientMaterial };
    }

    if self.is_in_check(self.side_to_move) {
        return GameStatus::Check { side: self.side_to_move };
    }

    GameStatus::Ongoing
}
```

> ⚠️ **与中国象棋规则的差异说明**：国际象棋中"无子可动"（stalemate）判**和棋**；中国象棋中判**负**。这是两个体系最容易混淆的差异点，必须有专门测试用例锁定。

### 5.2 子力不足判定

以下情形判和（双方均无法将死对方）：

| 红方剩余 | 黑方剩余 |
|---|---|
| 单帅 | 单将 |
| 单帅 | 单将 + 任意数量士/象 |
| 单帅 + 任意数量士/象 | 单将 + 任意数量士/象 |

> 说明：士/象无过河能力，无法参与将死对方；但**兵/卒、马、车、炮任一存在即不算子力不足**（即便只剩一个未过河的兵，理论上仍可助攻将死）。

### 5.3 简易子力不足的保守性

为避免误判和棋，采用**保守策略**：只有当双方都**仅剩**将帅 + 仕士 + 相象时判和。这是一条"宁可继续下，也不误判和"的取舍——因为误判和棋（把还能赢的判成和）比让对局继续（浪费一点时间）严重得多。

## 6. 重复局面与禁手

### 6.1 问题背景

中国象棋竞赛规则对"循环局面"（长将、长捉、长兑、一将一杀等）有详尽的裁决表，完整实现需要极其复杂的规则引擎（这是裁判级别的判定，规则文档中相关内容长达数十页）。

**本项目的策略：采用可实现、可解释的简化判定表，并在 UI 中明确展示裁决理由。**

> 这一取舍符合 [01-需求规格](01-需求规格说明书.md) 第 10 节的假设条款。业界主流在线象棋平台（含 JJ 象棋）同样采用简化裁定。简化不等于随意——本文档给出的规则是**确定性的、可测试的**，且与主流平台的实际行为一致。

### 6.2 重复局面检测机制

1. 每次 `make_move` 后，把当前 `hash` 压入 `history`；
2. 检测当前 `hash` 在 `history` 中是否已出现**两次以上**（即当前局面第 3 次出现）；
3. 若第 3 次出现，触发**裁决流程**。

> 用 `hash` 而非逐格比较是工程折衷：Zobrist 哈希在 64 位下碰撞概率极低（对单局数百步的规模，实际可忽略）。若需绝对严谨，可在哈希命中后再做一次逐格比对（**建议实现时采用此双重校验**，成本仅在对局出现重复时才付出）。

### 6.3 简化裁决表

触发三次重复后，检查**循环区间内双方着法的性质序列**：

| 循环内着法性质 | 裁决 | 说明 |
|---|---|---|
| **仅一方**持续将军（每一着均将军） | **该方判负** | 长将 |
| **双方**均持续将军 | **判和** | 双方长将 |
| **一方**持续捉同一棋子（每一着均捉） | **该方判负** | 长捉 |
| **双方**均持续捉子 | **判和** | — |
| 一方长将、另一方长捉 | **长将方判负** | 长将性质重于长捉 |
| 一方长将、另一方为闲着/兑子 | **长将方判负** | — |
| 其余所有情况 | **判和** | 含双方均为闲着、一将一杀等复合情形 |

**着法性质判定所需的能力**（由 `xq-core` 提供，`xq-coach` 复用）：

```rust
#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub enum MoveNature {
    Check,      // 将军
    Capture,    // 吃子（若吃的是"刚被捉的子"则同时构成"捉"的延续）
    Chase,      // 捉：下一步可吃掉对方某个未被足够保护的子
    Exchange,   // 兑：与对方等价交换
    Interpose,  // 垫子解将
    Escape,     // 避将（移动被将的将帅）
    CaptureAttacker, // 吃掉将军的棋子
    Idle,       // 闲着
}
```

**「捉」的精确定义（实现基准）**：

一步棋走后，若**下一步能吃到对方某个棋子**，且满足以下条件，则构成"捉"：

1. 被威胁的棋子不是将帅（那是"将"）；
2. 被威胁的棋子**不是无根子**或虽有根但吃后的交换对攻击方有利；
3. **关键排除项**：若该棋子是"因为攻击方的这一步而刚产生了新的保护"则不算；

> 「捉」的完整判定涉及"根"（保护关系）与交换价值的计算，这是整个规则模块中**最复杂的部分**。实现建议：先用"能吃到被攻击子且己方不亏"作为近似判据，再用测试用例逐步收敛。判定结果会被 `xq-coach` 直接用作讲解依据，因此宁可保守（少判"捉"）也不要误判。

### 6.4 自然限着

- `halfmove_clock` 在每次吃子时归零，其余情况递增；
- 达到 **120**（即 60 个完整回合）时判和；
- **例外**：若当前正处于将军状态，限着判定延后（避免"将军到最后一个回合就自动和棋"的荒谬情况）。

## 7. 着法表示与 make/unmake

### 7.1 着法编码

采用 **16 位紧凑编码**（2 字节），而非结构体，以降低搜索中着法列表的内存与拷贝开销：

```
 bit 15..8 | bit 7..0
   from   |   to
```

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
pub struct Move(pub u16);

impl Move {
    pub const fn new(from: u8, to: u8) -> Self { Move(((from as u16) << 8) | to as u16) }
    pub const fn from(self) -> u8 { (self.0 >> 8) as u8 }
    pub const fn to(self)   -> u8 { (self.0 & 0xFF) as u8 }
}
```

> 中国象棋无升变、无王车易位、无吃过路兵，因此只需 from/to 两个字段即可完全表达一个着法——这是相比国际象棋着法编码的巨大简化。**无需** promotion / castling 标志位。

### 7.2 `MoveRecord`（用于 unmake）

```rust
#[derive(Clone, Copy)]
pub struct MoveRecord {
    pub mv: Move,
    /// 被吃棋子（空 = 未吃子），unmake 时恢复
    pub captured: Square,
    /// 走子前的 halfmove_clock
    pub prev_halfmove_clock: u16,
    /// 走子前的 hash（用于回滚 Zobrist）
    pub prev_hash: u64,
}
```

### 7.3 `make_move` 步骤（严格顺序）

1. 从 `squares` 取出走子棋子与目标棋子；
2. 若目标有子：从 `squares` 移除 → 更新**对方**占据位图 → `halfmove_clock = 0`；
3. 否则 `halfmove_clock += 1`；
4. 移动棋子：更新 `squares` → 更新**己方**占据位图（清 `from`、置 `to`）；
5. 若移动的是将帅，更新 `red_king_sq` / `black_king_sq`；
6. 更新 Zobrist `hash`（异或：清 `from`、清被吃子、置 `to`、异或走子方）；
7. `side_to_move` 翻转；
8. 若走子方为黑，`fullmove_number += 1`；
9. 构造并压入 `MoveRecord`；
10. 压入新局面 `hash` 到 `history`。

> **步骤顺序必须严格遵循**，尤其是"更新占据位图"与"更新 king 缓存"必须在 `hash` 更新之前完成——否则会出现位图与棋盘不一致的隐蔽 bug。建议在 `#[cfg(debug_assertions)]` 下加入 `assert_consistent()` 校验函数，在每个 make/unmake 后调用（release 构建中消除）。

### 7.4 Zobrist 哈希

```rust
/// 固定种子的 Zobrist 表 —— 必须跨会话稳定！
pub struct Zobrist {
    /// 14 种棋子 × 90 格
    pub pieces: [[u64; BOARD_SIZE]; 14],
    /// 走子方为黑时异或
    pub side: u64,
}
```

**关键约束**：Zobrist 表必须用**编译期固定的种子**生成（例如常量 `0x9E3779B97F4A7C15` 作为 `StdRng::seed_from_u64` 的种子），**绝不能**使用 `thread_rng()` 或系统时间。原因：

1. 置换表（TT）若跨对局复用时，哈希必须一致；
2. 开局库/残局库的键基于哈希，必须稳定；
3. 测试需要可复现的结果。

> 这也正是 [ADR-005](14-决策记录ADR.md#adr-005) 要求领域层用"显式种子的 `StdRng`"的直接体现。

| 回合数 | 从 1 开始 |

### 8.2 棋子字母

| 字母 | 红方（大写） | 黑方（小写） |
|---|---|---|
| `K` / `k` | 帅 | 将 |
| `A` / `a` | 仕 | 士 |
| `B` / `b` | 相 | 象 |
| `N` / `n` | 马 | 马 |
| `R` / `r` | 车 | 车 |
| `C` / `c` | 炮 | 炮 |
| `P` / `p` | 兵 | 卒 |

### 8.3 标准初始局面（唯一正确形式）

```
rnbakabnr/9/1c5c1/p1p1p1p1p/9/9/P1P1P1P1P/1C5C1/9/RNBAKABNR w - - 0 1
```

**逐段校验**：

| 1 | 9 | `rnbakabnr` | 黑方底线：车马象士将士象马车 |
| 2 | 8 | `9` | 空行 |
| 3 | 7 | `1c5c1` | 空格 + 黑炮(`b7`) + 5 空格 + 黑炮(`h7`) + 空格 |

## 9. 中文记谱法

### 9.1 格式

```
<棋子名> <起点路数> <动作> <目标>
```

| 动作 | 含义 | 目标字段含义 |
|---|---|---|
| **进** | 向对方底线方向移动 | 见 §9.4 的棋子分档（格数或目标路数） |
| **退** | 向己方底线方向移动 | 同上 |
| **平** | 横向移动（同一行） | **目标路数** |

> ⚠️ **高频错误点**：「平」后面永远跟**目标路数**；「进 / 退」后面跟什么则取决于棋子 —— 详见 §9.4 的实现基准表。

### 9.2 进/退方向的判定

| 方 | 进（前进） | 退 |
|---|---|---|
| 红方 | `row` 增大 | `row` 减小 |
| 黑方 | `row` 减小 | `row` 增大 |

### 9.3 消歧（「前 / 后」规则）

当**同一条竖线上存在多个同种棋子**时，无法用路数唯一标识起点，改用「前 / 后」：

| 棋子数量 | 记法 |
|---|---|
| 2 个 | 「前 X」/「后 X」（省略路数） |
| 3 个 | 「前 X」/「中 X」/「后 X」 |
| 4 个及以上 | 「前 X」/「二 X」/「三 X」/ … /「后 X」 |

**「前 / 后」的判定**：

| 方 | 「前」 | 「后」 |
|---|---|---|
| 红方 | `row` **大**（更靠近黑方底线） | `row` 小 |
| 黑方 | `row` **小**（更靠近红方底线） | `row` 大 |

> 注意：红黑双方对"前后"的判断方向相反，因为双方各自的"前方"是对方底线方向。

### 9.4 转换示例（测试用例）

| 记谱 | 棋子 | 起点 | 目标 | 计算过程 |
|---|---|---|---|---|
| `炮二平五` | 红炮 | `h2`（col 7） | `e2`（col 4） | 红二路 = `9-7 = 2` ✔；平至五路 = `9-4 = 5` ✔ |
| `马二进三` | 红马 | `h0`（col 7） | `g2` | 红二路 = `9-7 = 2` ✔；"三"指的是**目标路数**（`g` 列 = 红三路）而非步数 |

> ⚠️ **易错点：「进 / 退」后面的数字到底是格数还是路数？**
>
> 答案**取决于棋子**。判据是「该棋子的纵向与横向位移是否固定」：
>
> - **斜行棋子**（马、相/象、仕/士）纵向与横向位移都是固定值，"走几格"信息量为零，
>   所以标**目标路数** —— 这才有意义。
> - **直行棋子**（车、炮、兵/卒、**帅/将**）位移长度是可变的，所以标**移动格数**。
>
> **实现基准（务必以本条为准）**：
>
> | 棋子 | 进 / 退 后的数字含义 |
> |---|---|
> | 车、炮、兵 / 卒、**帅 / 将** | **移动的格数** |
> | 马、相 / 象、仕 / 士 | **目标路数** |
>
> > 🔧 **本条已修正（2026-09-23 实现回写）**：原表把「帅 / 将」归入了「目标路数」一档，
> > 这是**错误的**。将帅只走直向一步，纵向移动时**起止路数相同**，若标目标路数就会
> > 出现「帅五进五」这种荒谬记法 —— 实际记谱必然是「帅五进一」。实现时按上表执行，
> > 并有 `notation::tests::doc_examples` 锁定该行为。
>
> 例如：
> - `车二进三` = 红车从 `h` 列（二路）向前走 **3 格** → `h0 → h3`
> - `马二进三` = 红马从二路走到**三路** → `h0 → g2`（`g` 列 = 红三路）
> - `炮八平五` = 红炮从八路（`b` 列）平到**五路** → `b2 → e2`
> - `兵七进一` = 红兵从七路（`c` 列）向前 **1 格** → `c3 → c4`
> - `帅五进一` = 红帅从五路向前 **1 格** → `e0 → e1`（**跟格数**，不是「帅五进五」）
>
> **数字字形**：红方用汉字数字（一二三四五六七八九），黑方用阿拉伯数字（1-9），
> 路数与步数**都**遵循这一规则。例如黑方 `炮8平5`、`卒1进1`。解析时两种字形都应接受。

**这是记谱模块最容易实现错误的地方，必须有覆盖全部七种棋子的测试用例集。**

### 9.5 往返测试要求

- 对随机对局的每一步生成中文记谱，再从记谱解析回 `Move`，必须与原着法一致；
- 用 `proptest` 生成 ≥ 10000 个随机局面 + 随机合法着法做往返测试；
- 特别构造"同一线多子"局面（双车、双马、三兵、五兵同列）验证消歧逻辑。

| 来源 | 用途 |
|---|---|
| 公开棋谱库（残局题集） | 验证"给定局面下的最佳着法" |
| 手工构造边界局面 | 覆盖极端情况（单仕、老兵、贴脸将） |
| 随机对局自对弈 | 用 `xq-ai` 自动对弈生成轨迹，验证全程无非法着法、无 panic |

**自对弈压力测试**：跑 1000 局 AI 自对弈，任一步出现 panic、非法着法、或终局状态矛盾即判定失败。这是覆盖面最广的回归手段。

## 12. 性能设计要点

| 优化点 | 手段 |
|---|---|
| 走法生成热点 | 按棋子类型分派；用查表代替重复的边界计算 |
| 边界检查消除 | 采用带哨兵边界的 12×11 内部表示可省去大量 `< 0` / `> 8` 判断（**进阶优化**，首版不引入，避免复杂度） |
| 内存布局 | `Move` 用 u16；着法列表预分配复用 `Vec`（`clear()` 而非重建） |
| 攻击检测 | 反向探测而非正向生成；优先检查最常见的攻击者（车/炮） |
| hash 更新 | 增量异或，不重算 |
| 调试断言 | `debug_assertions` 下开启一致性校验，release 下零开销 |
| 内联 | 热点小函数标 `#[inline]`；`Square` 编解码用 `const fn` |

**性能门禁**（`cargo bench`，CI 中监控劣化）：

| 基准 | 目标 |
|---|---|
| `perft(4)` | < 1 s |
| `legal_moves()`（初始局面） | < 1 µs |
| `is_attacked()` | < 100 ns |
| `make_move` + `unmake_move` 往返 | < 200 ns |
| 中文记谱转换（单着） | < 500 ns |

> 上表为设计目标，**须实现后用 `criterion` 实测并记录基线**，实际数值以实测为准。

## 14. 实现回写（2026-09-23 · M0 完成）

### 14.1 perft 基线：实测确认

[docs/03 §11.2](#112-perft-基准) 曾声明「除 depth 1 外均为公开资料值、未经独立验证」。
现由本实现实测确认，**五个深度全部与参考值一致**：

| 深度 | 节点数 | 实测结果 | 用时（release） |
|---|---|---|---|
| 1 | 44 | ✅ 一致 | — |
| 2 | 1,920 | ✅ 一致 | — |
| 3 | 79,666 | ✅ 一致 | — |
| 4 | 3,290,240 | ✅ 一致 | **221 ms** |
| 5 | 133,312,995 | ✅ 一致 | **9.91 s** |

复现命令：

```bash
cargo test -p xq-core --test perft                              # depth 1..3
cargo test -p xq-core --release --test perft -- --ignored       # depth 4..5
```

> ✅ **性能门禁达标**：§12 要求 `perft(4) < 1 s`，实测 **221 ms**，余量约 4.5 倍。
> 测量环境为开发机（Windows / `--release` / `lto=thin` / `codegen-units=1`），
> 后续 CI 若在不同硬件上运行，应重新记录基线而非沿用此值。

`perft(1) = 44` 的**逐棋子分解**已被 `movegen::tests::startpos_per_piece_breakdown_matches_doc`
锁定（车 4 / 马 4 / 相 4 / 仕 2 / 帅 1 / 炮 24 / 兵 5），因此若将来某个深度出错，
可以先从这张分解表定位到具体是哪类棋子的走法生成有问题。

> 📌 **一个易被忽略的细节**：走完「炮二平五」后，黑方合法着法数是 **45**，比初始的
> 44 多 1。原因是走的是 `h2` 那个炮，`h` 列让开后黑方 `h7` 炮向下的通路从 4 格延长
> 到 6 格；而 `b2` 的红炮原地未动，故 `b7` 炮仍是 12 步。若实现中出现 44 或 46，
> 说明对「炮架随局面变化」的处理有偏差。

### 14.2 与设计文档的偏差清单

| # | 偏差 | 理由 |
|---|---|---|
| 1 | Zobrist **不引入 `rand`**，改用内置 SplitMix64（种子仍为 `0x9E3779B97F4A7C15`） | [docs/02 §3.1](02-系统架构设计.md#31-依赖图严格单向无环) 规则 R1 规定 `xq-core` 不依赖任何内部 crate、仅 `serde`（可选）与零成本工具。自带 PRNG 反而更好：「不引入系统随机」由**代码结构**保证，而非靠约定 —— 根本不存在 `thread_rng` 可调用。实测 `cargo tree -p xq-core --edges normal` 只输出 `xq-core` 一行，**零运行时依赖** |
| 2 | `MoveRecord` 增加 `mover`、`prev_fullmove_number`、`gave_check` 三个字段 | §7.2 原字段**不足以完整回滚**：「回合数」在 `unmake` 时需要还原，而「走子方」在撤销后无法反推。`gave_check` 供重复局面裁决与 `xq-coach` 复用。三者都落在原有对齐填充内，结构体仍为 16 字节 |
| 3 | `§10` 的 `pub type Square = u8` 更名为语义明确的 `Piece` 约定（裸 `u8` + 命名辅助函数） | 「Square」在棋类编程里通常指**格子索引**，而这里指的是**格子上的棋子编码**。两者混用极易出 bug |
| 4 | `assert_consistent` **不再**加 `#[cfg(debug_assertions)]` 门禁 | 方法恒存在，只有库内部的调用点（`make_move` 的 `verify()`）在 debug 下触发。否则 release 构建的集成测试与基准无法调用它 |
| 5 | 合法性过滤中**排除「吃对方将帅」**的着法 | 从合法对局出发该情形永不出现，但手工构造的 FEN 可以摆出「对方将帅正被吃」的局面。若不排除，`legal_moves()` 会返回一步吃将着法，走完之后将帅缓存指向被占领格，触发一致性断言失败 |
| 6 | 新增 `mv.rs` 模块（§10 的模块清单中无此文件） | 承载 `Move` / `MoveList` / `MoveRecord`。放进 `position.rs` 会让单文件过度膨胀，且 `movegen` / `notation` / `fen` 都要依赖这三个类型，独立成模块后依赖关系更清晰 |
| 7 | 新增 `position_from_pieces` 辅助构造器 | 测试用：直接以 ICCS 坐标摆子构造局面，避免为每个用例手写 FEN |
| 8 | 中文记谱的「帅 / 将」分档**已修正**（见 §9.4 的修正说明） | 原表将帅将归入「目标路数」，会导致「帅五进五」这种荒谬记法。属**设计文档错误**，已在上文就地修正 |

### 14.5 记谱往返：补上消歧分支的覆盖（2026-09-25）

§9 要求「记谱往返：七种棋子 × 进/退/平 × **前后消歧** ≥ 80 用例」，§12 也把它列进质量门禁。
首版的往返测试（`roundtrip_from_startpos`、`chinese_notation_roundtrip_is_lossless`）
只覆盖了**开局局面**，而消歧字形要「同一条竖线上有两个以上同种同色棋子」才出现 ——
开局一个都没有。于是 `Subject::Front/Back/Middle/Nth` 那条**渲染**分支虽然各有单测
（`front_back_disambiguation_with_two_pieces` 等），却从来没被**往返**验证过。
它恰恰是唯一会输出非路数前缀的地方，渲染错也看不出来。

现补 `roundtrip_covers_disambiguation_glyphs`：同线两车 / 三车 / 五兵三个局面，
逐个合法着法生成记谱再解析回来，并**断言四种消歧形式都真出现过**
（`front` / `middle` / `back` / `nth`）—— 否则局面摆错或分支没走到，测试照样「通过」。

顺带修一处诊断缺陷：**字形认识、但不属于当前走子方**时，原先报的是
`UnknownPieceChar`（「无法识别的棋子字: 馬」）。而 `馬` 正是界面自己输出的字形之一，
照着输却被告知「不认识这个字」，只会把人往「我是不是打错字了」的方向引。
现拆成两个错误码：

| 情况 | 提示 |
|---|---|
| 字真不认识（如 `龍`） | 无法识别的棋子字: 龍 |
| 字认识，但不属于当前走子方 | 「馬」是黑方的字形，现在轮到红方走 |

> ⚠️ 触发这次排查的报障（「输入界面输出的记谱却报错」）后来查明是**假警报**：
> `馬8进7` 被拒是因为当时轮到**红方**走；`俥一平二` / `车一平二` 被拒是因为
> 红车被自己的马挡着、**那一步本来就非法**。往返不变量本身一直是成立的 ——
> 缺的是上面那条覆盖，和一条能把话说清楚的错误提示。

## 1. 项目背景与目标

### 1.1 背景

现有中国象棋产品（以 JJ 象棋为代表）在**对战功能性**上已相当成熟，但普遍存在一个共同短板：**只告诉你怎么走，不告诉你为什么**。新手输棋后无法定位"我哪一步走坏了、坏在哪、正确思路是什么"，学习闭环缺失。

### 1.2 产品目标

构建一个跨平台中国象棋客户端 + 联网对战服务端，**核心差异化是"战法讲解"**：每一步落子后，系统在棋盘旁边给出结构化点评——着法名称（如"中炮过河车"）、战术标签（如"捉双"）、意图说明、以及相对最优着法的评价等级（优/良/疑/劣/漏）。

### 1.3 成功判据（可量化）

| 指标 | 目标值 | 度量方式 |
|---|---|---|
| 规则裁决正确率 | **100%** | 对拍题库（≥3000 局面）全通过 |
| 走棋本地响应 | **≤ 16 ms** | 客户端埋点 P95 |
| 走棋提示生成 | **≤ 50 ms** | 客户端埋点 P95 |
| AI 首步响应（中级档） | **≤ 1 s** | 引擎基准测试 |
| 联网对战端到端延迟 | **≤ 150 ms** | 同区域机房，P95 |
| 服务端单机并发对局 | **≥ 2500 局** | 压测（5000 WS 连接） |
| 战法讲解覆盖率 | **≥ 95%** 的着法有非空讲解 | 离线统计 1000 局棋谱 |
| 讲解准确率 | 人工抽检 **≥ 90%** 无事实性错误 | 抽检 200 条讲解 |

## 2. 术语表

### 2.1 象棋领域术语

| 术语 | 定义 |
|---|---|
| **着法 / Move** | 一步棋，含起点、终点 |
| **回合 / Round** | 红方走一步 + 黑方走一步 = 1 回合 |
| **九宫 / Palace** | 将帅活动区域，3×3 格，位于棋盘纵线 4-6、横线 1-3（红）与 8-10（黑） |
| **河界 / River** | 棋盘第 5、6 横线之间的区域，兵卒过河后获得横向走子能力，象/相不可逾越 |
| **将军 / Check** | 一方的棋子下一步可吃掉对方将帅 |
| **将死 / Checkmate** | 被将军且无任何合法着法可解 |
| **困毙 / Stalemate** | 未被将军但无任何合法着法（**中国象棋中困毙方判负**，与国际象棋判和不同） |
| **白脸将 / Flying General** | 将帅在同一直线上且中间无子，属非法局面，等同于被将军 |
| **蹩马腿** | 马前进方向上紧邻点有子，则该方向的两个走法被禁止 |
| **塞象眼** | 象/相田字中心点有子，则该方向走法被禁止 |
| **炮架** | 炮吃子时必须恰好隔一个棋子，该棋子称炮架 |
| **长将** | 一方连续将军形成循环局面，判该方负 |
| **长捉** | 一方连续追捉同一棋子形成循环局面，判该方负 |
| **自然限着** | 连续 60 回合双方均无吃子，判和 |
| **中炮 / 当头炮** | 炮二平五类着法，攻击中路 |
| **闷宫** | 将帅被己方棋子堵死退路而被将死 |
| **抽将** | 通过将军同时吃掉对方棋子的战术 |
| **捉双** | 一步棋同时攻击对方两个棋子 |

### 2.2 系统术语

| 术语 | 定义 |
|---|---|
| **引擎 / Engine** | 规则裁决模块 `xq-core`；有时特指 AI 搜索模块 `xq-ai`，本文档中"AI 引擎"专指后者 |
| **教练 / Coach** | 战法讲解模块 `xq-coach` |
| **权威裁决 / Authoritative Validation** | 由服务端执行的、具有最终效力的规则校验 |
| **乐观更新 / Optimistic Update** | 客户端先本地渲染着法再等服务端确认的交互策略 |
| **P95 / P99** | 95% / 99% 分位数延迟 |
| **NPS** | Nodes Per Second，引擎每秒搜索节点数 |

| 角色 | 描述 | 核心诉求 |
|---|---|---|

| **运营管理员 / Admin** | 平台运营人员 | 举报处理、封禁、赛季配置、监控 |

**关键需求详述 — FR-01.06 终局判定**

中国象棋的终局判定与国际象棋存在**关键差异**，必须严格按中国规则实现：

| 情形 | 判定 |
|---|---|
| 被将军且无合法解 | **将死，被将死方负** |
| 未被将军但无任何合法着法 | **困毙，被困毙方负**（国际象棋此情形判和） |
| 连续 60 回合（120 着）双方均无吃子 | 判和 |
| 双方均只剩单将 | 判和 |
| 一方长将，另一方应将 | **长将方负** |
| 双方均长将 | 判和 |
| 自然限着已达但一方仍在将军 | 不判和，继续 |

**关键需求详述 — FR-03.03 评价等级判定基准**

评价以"该着法与引擎最优着法的**评估分损失**（Score Loss，单位：厘兵，centipawn）"为客观基准：

| 等级 | 分差区间 | 用户可见文案 | 色阶（取自 design-tokens） |
|---|---|---|---|
| 优 Best | 分差 ≤ 10 | 「最佳着法」 | `coach.best` #27AE60 |
| 良 Good | 10 < 分差 ≤ 50 | 「不错」 | `coach.good` #2E86DE |
| 疑 Dubious | 50 < 分差 ≤ 150 | 「稍有问题」 | `coach.dubious` #F39C12 |
| 劣 Blunder | 150 < 分差 ≤ 400 | 「明显失误」 | `coach.blunder` #E74C3C |
| 漏 Missed | 分差 > 400 或错失必胜 | 「严重漏着」 | `coach.missed` #8E44AD |

> 注：分数单位"厘兵"= 1/100 个兵的价值。兵的基准分值由评估函数定义，见 [docs/04-AI引擎设计.md](04-AI引擎设计.md)。
> 分档阈值需用真实对局样本**回测校准**，不得凭感觉设定——校准方法与数据集见 [docs/12-测试策略与质量保障.md](12-测试策略与质量保障.md)。

**关键需求详述 — FR-05.06 断线重连**

重连必须恢复的状态清单（缺一不可）：

1. 对局元信息：房间号、双方身份、执子颜色
2. 完整着法历史（用于重放棋盘）
3. 双方剩余局时、当前步时剩余毫秒
4. 当前轮到谁走、是否处于将军状态
5. 已产生的讲解历史（用于讲解面板）
6. 悔棋/求和请求的待决状态

> 重连策略采用「**全量快照 + 增量补帧**」：服务端先下发 `SessionResumed`（含完整快照），再补发断线期间遗漏的帧（以服务端维护的单调递增 `seq` 为准），最后转入实时流。详见 [docs/06-联网对战与实时通信协议.md](06-联网对战与实时通信协议.md)。

## 7. 需求边界（明确不做）

| 范围外项 | 原因 |
|---|---|
| 移动端 App（iOS / Android） | 本期聚焦桌面三端；WASM 可复用为后续 Web 版基础 |
| 直播推流 / 视频解说 | 属内容运营范畴，非棋类核心 |
| 支付、道具商城、会员 | 商业化另立项 |
| AI 模型训练平台 | 本期使用经典搜索 + 手工评估；NNUE 训练另立项 |
| 象棋变体（揭棋、翻翻棋、暗棋） | 规则差异大，另立项 |
| 国际象棋 / 将棋 | 规则体系完全不同 |
| 自建账号体系的短信验证 | 依赖第三方短信服务，P2 再评估 |

## 8. 验收标准（版本准入）

### 8.1 M1（离线版）准入

- [ ] `cargo test -p xq-core` 全绿，对拍题库 ≥ 3000 局面 100% 通过

## 10. 假设与约束

| 类型 | 内容 |
|---|---|
| 假设 | 规则遵循中国象棋竞赛规则（2011 版）体系；长捉等复杂禁手的裁决采用**可实现的简化判定表** |

| 约束 | 客户端必须支持完全离线的人机对战与本地讲解 |
| 约束 | 三端使用同一份 Rust 规则代码，禁止各端分别实现规则 |
